# End-of-Day (EoD) Update Scoring SOP

This document defines the rules for formulating high-quality daily work remarks and scoring them according to the team's End-of-Day reporting Standard Operating Procedure (SOP). All factual statements must be grounded in verified Git evidence and user notes.

---

## 1. Per-Task Score (Maximum 5 Points)

Each eligible task entry receives a score based on three dimensions:

$$\text{Task Score} = \text{Consistency} + \text{Timeliness} + \text{Quality} \quad (\le 5.0)$$

### A. Consistency (Max 1.0 Point)
* **+1.0**: Logged on an official weekday (Monday through Friday).
* **0.0**: Logged on a weekend (weekends are excluded from standard score calculations).

### B. Timeliness (Max 1.0 Point)
Measured against the employee's official start time plus 9 hours (the standard shift end):
* **+1.0**: Submitted on or before $\text{Start Time} + 9\text{ hours}$.
* **+0.5**: Submitted within the grace hour ($\text{Start Time} + 9\text{h}$ to $+10\text{h}$).
* **0.0**: Submitted later than 1 hour past shift end.
* *Note:* Requires verified employee start time and local timezone; if unknown, label timeliness as unverified rather than assuming full marks.

### C. Quality (Max 3.0 Points)
* **0.5**: Minimal text (< 10 characters) or generic filler ("same as yesterday", "continue task").
* **1.0**: Short, incomplete text (< 5 words), vague activity without technical context.
* **2.0 – 3.0**: Cohesive, descriptive technical narrative prose (5–8 sentences) containing:
  * **+0.5**: Clear problem context, approach, and concrete behavior/progress implemented.
  * **+0.5**: Explicit validation, build verification, or automated/manual testing performed.
  * **+0.5**: Real technical obstacles, challenges, or constraints encountered and how they were resolved (or external ticket dependencies).
  * **+0.5**: Clear next step in the implementation or verification plan.
  * **+0.5**: Natural, connected human prose flow (5–8 sentences in a single paragraph without robotic bullet-point lists).
  * *Quality score is strictly capped at 3.0 points.*

---

## 2. Weekly Adjustments & Eligibility

* **Weekly Bonus (+2.0 points)**: Awarded if the employee records valid task updates on all 5 weekdays in the reporting week.
* **Repetition Penalty (-5.0 points)**: Deducted if 3 or more consecutive workdays have nearly identical remarks ($\ge 95\%$ text similarity).
* **Waiting Task Exclusion**: Tasks marked with status `Waiting` do not generate task points and do not count as active update days. Do not artificially move tasks out of Waiting solely to gain points.
* **Zero Padding**: Never artificially split a single task into multiple tickets or pad entries with filler to inflate metrics.

---

## 3. Weekly Employee Summary Metrics

$$\text{Final Weekly Score} = \sum \text{Eligible Task Scores} + \text{Bonus} - \text{Penalty}$$
$$\text{Average Score / Day} = \frac{\text{Final Weekly Score}}{\text{Total Valid Update Days}}$$

* **Total Task Entries**: Count of distinct tasks updated with valid remarks.
* **Total EoD Update Days**: Number of distinct weekdays with at least one verified update.
* If update days $= 0$, average score is `N/A` (do not divide by zero).

---

## 4. Mandatory Writing Style: 5–8 Sentence Human Narrative Prose

Every work remark generated by `kanban-updater` must be written as **a single, cohesive paragraph of 5 to 8 sentences** in plain, natural human engineering English. **Do not use bullet-point lists** (`- Progress:`, `- Validation:`, etc.).

### Core Style Rules
1. **No Self-Ticket / Work Item Numbers**:
   * Never mention the current ticket/work item number inside the remark text (since the remark is posted directly inside that card).
   * **Exception**: Only mention a work item/ticket number when referencing an **external dependency or blocker on another ticket** (e.g., *"blocked until #7412 is deployed"*).
2. **Follow the Natural Engineering Story Arc (5–8 Sentences)**:
   * **Sentence 1 — Problem & Goal ("Why")**: State what is being built or fixed and why the old behavior was insufficient.
   * **Sentences 2–3 — Existing Behavior & Chosen Solution ("How & What")**: Explain what the code already did versus the chosen solution, business rules, and edge cases/states handled.
   * **Sentence 4 — Refinements & Design Decisions** *(when applicable)*: Mention wording, layout, or architectural adjustments made after review or testing.
   * **Sentences 5–6 — Obstacles / Challenges & Validation**: Describe any build failures, DLL/dependency mismatches, or tricky bugs hit, how they were traced and resolved, and what builds/tests/screenshots verified the fix.
   * **Sentence 7 — Next Progress in the Plan**: Close with the next concrete step (remaining test cases, edge-case checks, or opening the PR).
3. **Plain, Human Developer Tone**:
   * Write the way a developer explains their day to a teammate ("already read ... but discarded them, so they are now kept", "The first local build failed because ... which was traced and resolved by ...").
   * Avoid stiff AI buzzwords ("leveraged", "spearheaded", "seamlessly orchestrated", "comprehensive refactoring").

### Gold-Standard Reference Example (7 Sentences)

> Show the AI Plus license expiration date in Flippy's settings, since the License tab gave no date and an expired license only said "License expired". Flippy already read the start and end dates from the license file but discarded them, so they are now kept and shown as "Expires: \<date\>", with the days left and an amber box only in the last 30 days, the same rule Synergy uses for its own license warning. Expired and not-yet-started licenses now show their date in red, and "Ask your administrator to renew the license." appears below the box when action is needed. The wording and layout were refined after review: no day count for far-away dates, no repeated "valid", and the hint names the customer's administrator. The first local build failed because the latest master needs a newer AIPlusAgentCore DLL, which was traced and resolved by updating it, after which the full build passed and a 2030 license showed correctly in Flippy. Documentation screenshots of every license state were produced with automated browser tests on the real settings page. Will test near-expiry, expired and not-started cases with real licenses from the license generator and create the PR.

### Anti-Patterns to Avoid
* **Bullet-Point Dump**: Using `- Progress:`, `- Validation:`, `- Pending checks:`, `- Proposed next step:` instead of connected prose sentences.
* **Repeating the Current Ticket Number**: Starting with *"For work item #7111, I implemented..."* when the remark is already inside ticket `#7111`.
* **Hallucination**: Inventing unmentioned collaborators, unverified root causes, or undeployed releases not backed by Git evidence or user notes.

## 5. Mandatory Self-Audit Before Presenting a Work Log

Every work log (both modes) is inspected and scored before the user sees it. Show the result as a short table under each card's remark.

### A. Inspection (needs card history: `synergy_fill.py history`)

| Check | Rule |
|---|---|
| Already logged today? | If `today_logged` is true, show today's entry and ask whether to add a second entry or skip the card. |
| Repetition | Compare the draft with `recent_texts`. If it is ≥ 95% similar to an entry from the last 3 workdays, rewrite it around what is actually new today. Three near-identical days trigger the −5.0 penalty. |
| Continuity | If the last entry named a next step, say whether it was done today. |
| Status | Cards in `Waiting` earn no points; note it, and never suggest moving a card only to gain points. |
| Gap days | If `by_date` shows missed weekdays, mention them to the user; never back-date or invent work for them. |

When history cannot be read (Work Log mode without browser access, or the read failed), say "history not checked" in the audit table instead of guessing.

### B. Scoring (this file, sections 1–3)

| Dimension | What to report |
|---|---|
| Consistency | +1.0 if today is a weekday, else 0. |
| Timeliness | Expected points if submitted now, from `start_time` + 9h (grace +10h). "unverified" when `start_time` is not set. |
| Quality | Points per criterion in section 1.C (problem and approach, validation, obstacles, next step, natural prose), capped at 3.0. |
| Expected task score | Sum, at most 5.0. |

### C. Gate

* Revise the draft until quality is at least 2.5, unless the evidence for the day is genuinely thin. In that case say what is missing and ask the user for a note rather than padding.
* Never inflate: no invented validation, blockers, or next steps to collect points.
